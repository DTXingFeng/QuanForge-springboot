制定日期：2026-11-14。面向没有量化经验的项目所有者。

补充授权：使用者已明确允许自主修改模拟交易策略开展测试，无需逐个确认普通策略和参数选择。可以并列建立有限候选实验，保留全部失败结果和旧版本；每轮开始前固定样本、成本及规则，修改后另建版本。原有不切换真实资金、不覆盖历史、不擅自部署生产的限制继续适用。已登记的旧实验不因这项授权而改写。

## 目标和当前起点

第一目标是建立一个能解释每笔交易、能在故障后恢复、账目能核对的模拟交易系统。第二目标才是检验策略扣除成本后是否具有预测优势。工程验收通过不等于策略赚钱，最终结论允许是“策略失败”或“证据不足”。

依据是 [2026-11-12 审计报告](audit-20261112/REPORT.md)及其测试和交易证据。本计划已重新读取本地报告和工作区变更，但没有刷新树莓派运行状态；报告中的服务、账户和仓位状态只代表当时观察。旧版 QuantForge 不在范围内。

已完成的审计修复留在本地，不能当作已经部署。已有实验证明部分成交、止损和状态处理错误得到修正，但尚未证明策略净收益改善。当前仍缺订单幂等与所有权、组合资金约束、可靠净账、统一行情时点及盘中保护闭环。

## 工作安排

按验收结果推进，不按“运行了几天”自动升级。前四阶段以隔离环境和虚拟账户为对象，不向交易所账户发测试订单。

| 阶段 | 我负责的工作 | 交付与过关标准 |
| --- | --- | --- |
| 0. 固定可追溯基线 | 再次只读核对树莓派进程、实际程序与仓位来源；保留现有差异，确定 Java 与 Python 影子程序的责任边界 | 运行清单、代码哈希、数据备份与差异表；每个交易出口都有明确账户和归属，未知项保留为阻碍 |
| 1. 交易生命周期 | 请求前保存交易意图；稳定订单编号；超时先对账；重启恢复；并发去重；账户级资金预留；异常时禁止新开仓但继续保护旧仓 | 同一意图不产生重复敞口；模拟已受理但丢响应后不盲目重下；真实子进程崩溃/重启后可恢复责任；退出必须确认 |
| 2. 逐笔净账 | 将意图、订单、成交、止损变更、平仓、手续费与资金费串联；记录未实现盈亏及未知状态 | 每笔能回答“为何开、为何平、实际成本”；钱包资金变动可核对，误差按资产精度解释；未知损益不得记为零或剔除 |
| 3. 数据和故障验收 | 统一信号、AI、风控及下单的行情时点；拒绝过期/缺口数据；按止损实际生效时间回放；完成盘中保护和停机接管设计 | 正常、急涨、急跌、极端波动、断网、重启、超时/重复响应、缺失/乱序均有可复现实验；相同输入保留修复前后结果 |
| 4. 单策略前向 PAPER | 固定一个规则可解释的策略作为实验对象；冻结版本、参数、品种、成本及评估规则；接入新到达的行情，仅本地模拟成交 | 完整记录全部信号和交易，区分成交假设与实际价格；报告净收益、净值回撤、次数、成本、退出延迟和异常数量；无工程阻碍才讨论 Demo |
| 5. 受控 Demo 验证 | 准备具体部署与回退包，获准后才变更树莓派或启动交易所模拟下单；先核对账户、保护单和恢复流程 | 验证真实接口下的订单、成交、仓位与账本一致性；阶段结论独立于 PAPER，不把 Demo 成绩当实盘收益 |
| 6. 检验策略及 AI 增益 | 在独立未来样本上判断规则策略是否有净优势；之后用相同输入和成本比较固定规则与 AI 辅助 | 报告不确定性及失败结果；AI 只有带来可重复的增益且未增加执行异常才考虑进入决策链路 |

阶段 1 和 2 的事件记录共同设计，避免先写交易器、事后再猜交易归属。每个工作包交付代码差异、失败复现、修复后结果和剩余限制。避免整项目重写，不重复运行无关测试。

## 下一个具体工作包

先实现“一个订单从意图到确认退出的完整闭环”，从现有 Java 执行路径切入，暂不增加策略数量或训练新模型。

1. 保存当前代码和数据库结构基线，列出所有可能发单或把交易降级为 PAPER 的路径。
2. 先复现三个故障：交易所已受理但客户端超时；两个任务同时开同币种仓位；进程在发单或回写数据库之间退出。
3. 最小修复：持久化交易意图和事件、稳定唯一订单编号、状态未知时暂停相关新开仓并对账、数据库约束及资金预留。
4. 补测部分成交、撤单与成交竞态、重复响应、数据库提交失败；旧仓保护和退出不因暂停新仓而停止。
5. 用隔离 SQLite、模拟接口和实际子进程重启验证，记录重复订单数、无人管理仓位数、账本差额、恢复时长及仍未知的事件。

验收目标是上述受控场景中重复敞口和失管仓位均为零，资金不被重复预留或提前释放，未知状态明确可见。有限测试不能证明所有生产故障都已消除。

订单编号只帮助关联和去重，不能把“发送成功”当作“成交成功”，也不能单靠编号宣称实现跨进程幂等。编号规则和保护参数以 [Bybit 官方下单文档](https://bybit-exchange.github.io/docs/v5/order/create-order)为依据，交易结果仍需后续订单、成交及仓位事件核对。

## 初期实验的默认选择

- 一个策略、一个预先确定的交易品种、最多一个在场仓位，减少归因混乱。具体品种在检查数据完整性和流动性后确定并冻结，不按历史盈利排名选择。
- 本地 PAPER 初期总名义敞口不超过虚拟净值，风险预算同时计入在途委托；这只是工程实验约束，不是收益最优参数或实盘建议。
- 开始前锁定单笔风险、日损失和总回撤停止阈值并写入实验配置。触发后保留全部数据；禁止用调高阈值延长亏损实验。阈值并不保证跳空或故障时实际损失不会超出。
- AI 初期仅记录建议及理由，不直接改仓位。规则策略也只是待检验对象，不因旧样本偶然盈利而获得优先信任。
- 成本包含双边手续费、资金费和明确的滑点假设；未知资金费和缺失价格单独标记。测试收益对合理成本变化是否敏感，但不选择最漂亮的成本假设。
- 所有旧失败策略和结果保留在研究记录中。研究数据、调参数据和最终验证数据分开；已经看过的样本不能重新标成未见测试集。

## 何时停、何时继续

发现重复订单、仓位归属不明、保护失效、行情过期或账目无法解释时，禁止新增风险并保留现有仓位的管理与对账。不能简单杀掉进程后留下仓位。先复现、再修复、再跑同一场景。

策略评估开始前，根据实际信号频率确定固定观察窗口和分析日期；初次四周可作工程与数据质量复核，但不能自动作为盈利验收。交易高度相关时，笔数多也不代表独立证据充分。报告应给出净收益的不确定性、不同市场区间的表现、尾部损失及成本敏感性。

观察窗口结束后，若扣费表现差或证据不足，就明确记录失败或不足。每轮研究只允许预先登记的有限候选；修改参数后重新使用独立样本，不反复在同一测试集上优化。策略没有优势时，不靠放大杠杆解决。

## 使用者需要知道的几个词

| 术语 | 在本项目里的意思 |
| --- | --- |
| 历史回测 | 用过去的数据检验规则，结果依赖数据、撮合与成本假设 |
| PAPER | 本地记账模拟交易，不产生交易所订单 |
| Demo | 在交易所模拟环境发单，可验证接口行为，仍不等同于真实资金交易 |
| 净收益 | 把手续费、资金费等成本扣除后的收益；仍需说明滑点如何计入 |
| 最大回撤 | 资金净值从某个高点到后续低点的最大跌幅，不能只统计已平仓盈利 |
| 敞口/杠杆 | 实际承受价格变化的仓位规模及其相对账户资金的倍数；倍数越大，同样价格变动的资金影响越大 |

## 分工和授权边界

技术方案、测试设计、数据核验、最小修复、普通参数解释及结论由我负责。使用者无需先学会指标选择，也不需要替我判断普通技术方案。

已有授权支持本地审计修复、隔离测试及必要的只读取证。生产部署、服务重启、修改真实凭证、账户订单和新增付费服务不包含在本计划执行许可内；涉及这些动作时先准备可审阅结果，再就具体动作确认。本计划没有真实资金交易阶段。原始交易历史不得删除、覆盖或为了收益好看而筛掉。

每次交付用四句话说明：完成了什么、证据是什么、还有什么不能相信、下一步做什么。无需使用者盯盘，也不承诺当前会话结束后存在未经设置的后台运行。
